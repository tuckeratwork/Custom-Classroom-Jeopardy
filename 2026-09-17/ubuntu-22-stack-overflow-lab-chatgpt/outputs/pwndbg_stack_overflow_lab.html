Seeing a Stack Buffer Overflow

A guided, local-only lab for students with minimal computer-architecture experience. You will build a deliberately vulnerable teaching program, watch its stack frame appear one instruction at a time, and use printable marker bytes to see a saved frame pointer and return address become corrupted.

Lab contents
1. Outcomes and scope2. Mental model3. Install tools4. Build the program5. Learn Pwndbg6. Watch the frame form7. Safe copy baseline8. Marked overflow9. leave and ret10. Frame lifetime11. Restore defenses12. QuestionsCommand reference

1. Outcomes and laboratory scope

By the end, you should be able to explain what EIP, EBP, and ESP do; distinguish live registers from saved values in memory; locate a local buffer, compiler padding, saved EBP, return address, and first parameter; and explain why leave and ret reveal an overwrite only when the function returns.

Scope: run this only in your own Ubuntu lab VM. The exercise uses a purpose-built local binary, a non-executable stack, and printable A/C/B/X markers. It does not inject code, open a shell, contact a network service, or target third-party software.

Estimated time: 75–110 minutes. Evidence to submit: the screenshots called out in dashed boxes, a completed stack diagram, and answers to the review questions.

2. Mental model: code, registers, and the stack

The function’s machine instructions stay in the executable’s code mapping. A function call does not copy those instructions onto the stack. Instead, the stack holds short-lived call data: parameters, a return address, saved register values, and local variables.

RegisterPlain-language jobWhere its value comes from
EIPInstruction pointer: address of the instruction currently being executed.The CPU advances it after ordinary instructions. call, branches, and ret replace it with another code address.
ESPStack pointer: address of the current top of the stack.push, pop, call, ret, and explicit arithmetic change it. On 32-bit x86, pushes move it toward lower addresses.
EBPFrame pointer: a stable reference point for the current function’s frame.The usual prologue saves the caller’s EBP, then copies ESP into EBP. The compiler addresses locals below it and parameters above it.
HIGHER ADDRESSES [EBP+8] first parameter: a pointer to the source string [EBP+4] saved return address ── ret later loads this into EIP [EBP] saved caller EBP ── leave later pops this into EBP [EBP-8] compiler padding ... [EBP-40] buffer[0] ── local 32-byte array begins here ↑ ESP at our chosen checkpoint LOWER ADDRESSES (the stack grows in this direction)
Do not mix up a slot with its contents. The slot at [EBP+8] contains a four-byte pointer value. That pointer identifies where the input characters live. It is data, not an instruction.

3. Install the 32-bit toolchain and Pwndbg

AInstall the compiler and 32-bit libraries

Bash — package setup
sudo apt update
sudo apt install -y build-essential gcc-multilib libc6-dev-i386 git gdb

sudo runs the package operation with administrator rights. apt update refreshes Ubuntu’s package index. build-essential supplies the normal C build tools; gcc-multilib and libc6-dev-i386 let a 64-bit Ubuntu host compile and link 32-bit programs; git downloads Pwndbg’s repository; and gdb is the debugger Pwndbg extends.

BInstall Pwndbg from its GitHub repository

Bash — official source install
cd ~
git clone https://github.com/pwndbg/pwndbg
cd pwndbg
./setup.sh

cd ~ moves to your home directory. git clone creates a local copy of the official repository. cd pwndbg enters it. ./setup.sh installs Pwndbg’s dependencies and configures GDB to load it. If the repository already exists, do not clone a second copy; enter it and follow the project’s update instructions instead.

Dated compatibility note (September 2026): the Pwndbg project currently lists GDB 12.1+, Python 3.10+, and Ubuntu 22.04/24.04 as supported. Its maintainers have discussed ending source-install support for Ubuntu 22.04 after October 2026; the official portable GDB package is the fallback if a future source version no longer installs on Jammy.

gdb -q starts GDB without its long banner. A pwndbg> prompt and a Pwndbg version line confirm that the extension loaded. quit exits.

4. Create and compile the teaching program

Create a working folder, then save the supplied stack_lab.c there. The complete source is also shown below.

Bash
mkdir -p ~/stack-frame-lab
cd ~/stack-frame-lab
C — stack_lab.c
#include <stdio.h>
#include <string.h>

__attribute__((noinline))
void copy_label(const char *student_text)
{
    char buffer[32];

    puts("Inside copy_label()");
    printf("  buffer starts at %p\n", (void *)buffer);

    /* Intentionally unsafe for this local, controlled teaching lab. */
    strcpy(buffer, student_text);

    printf("  first 32 bytes: %.32s\n", buffer);
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "Usage: %s TEXT\n", argv[0]);
        return 1;
    }

    copy_label(argv[1]);
    puts("copy_label() returned normally.");
    return 0;
}

buffer[32] reserves 32 bytes in each active invocation of copy_label. student_text is a pointer parameter. strcpy copies bytes until a terminating zero byte and does not know the destination size—this is the deliberate defect. noinline prevents the compiler from merging the function into main.

Bash — compile on one line
gcc -m32 -O0 -g3 -Wall -Wextra -fno-stack-protector -fno-omit-frame-pointer -fno-pie -no-pie -U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0 -z noexecstack -o stack_lab32 stack_lab.c
OptionPurpose in this lab
-m32Generate 32-bit x86 code, so the registers are EIP/EBP/ESP and stack words are four bytes.
-O0Disable optimization so the source, frame, and disassembly remain easy to follow.
-g3Include detailed debug symbols so GDB knows names such as buffer.
-Wall -WextraEnable useful compiler warnings.
-fno-stack-protectorTurn off the canary only for this teaching binary so the saved frame data remains observable.
-fno-omit-frame-pointerKeep the EBP-based frame used by the lesson.
-fno-pie -no-pieProduce a non-PIE executable so code addresses are stable across runs.
-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0Disable fortified library replacement for this one binary.
-z noexecstackKeep the stack non-executable; this lab demonstrates corruption, not code execution.
-o stack_lab32 stack_lab.cName the output binary and specify the input source file.
Bash — verify and test
file ./stack_lab32
readelf -W -l ./stack_lab32 | grep GNU_STACK
./stack_lab32 SAFE_INPUT

file should report a 32-bit Intel 80386 ELF with debug information. readelf inspects program headers; GNU_STACK should show RW, not RWE. The final command supplies a short safe argument and should return normally.

6. Watch copy_label build its frame

Checkpoint 1 — before the call

Bash
cd ~/stack-frame-lab
gdb -q ./stack_lab32
Pwndbg
set pagination off
set disassembly-flavor intel
disassemble main

In the disassembly, find the instruction call copy_label. Copy its address from the left column, then substitute it below. The address is determined from your binary instead of assumed from a screenshot.

Pwndbg — replace the placeholder
break *CALL_ADDRESS
run SAFE_INPUT
regs eip ebp esp
nearpc
telescope $esp 4
p/x &buffer

break *ADDRESS places an instruction breakpoint; the asterisk means “break at this exact machine address.” run SAFE_INPUT starts the program with one argument. Before call, ESP points at the already-pushed pointer parameter. The expected p/x &buffer result is “No symbol … in current context,” because copy_label is not active yet and its local object does not exist.

Checkpoint 2 — after call

Pwndbg
si
regs eip ebp esp
nearpc
telescope $esp 3

si means “step one machine instruction.” The CPU has now pushed the address of the instruction after call and changed EIP to the first instruction of copy_label. EBP still belongs to main. At [$esp] you should see the saved return address, and at [$esp+4] the parameter pointer.

Checkpoint 3 — execute the prologue

Pwndbg — execute and inspect each instruction separately
si
regs eip ebp esp
telescope $esp 3
si
regs eip ebp esp
telescope $ebp 3
si
regs eip ebp esp
p/x &buffer[0]
p/x &buffer[31]
p/x &buffer[32]
distance &buffer[0] $ebp
telescope $ebp-0x28 13

The three instructions should be push ebp, mov ebp,esp, and sub esp,0x28. The push stores main’s EBP. The move makes EBP the new frame anchor. The subtraction reserves 0x28 hexadecimal = 40 decimal bytes. Only 32 belong to buffer; in this build the remaining eight are compiler padding. The bytes are reserved but not initialized, so old-looking values are expected.

7. Establish the safe-copy baseline

First locate the source line immediately after strcpy:

Pwndbg
list copy_label

In the supplied file, the following printf is line 15. If your editor inserted lines, use the line number shown by list.

Pwndbg — replace POST_COPY_LINE if necessary
break stack_lab.c:15
continue
regs eip ebp esp
whatis buffer
p/d sizeof(buffer)
p/x &buffer[0]
p/x &buffer[31]
p/x &buffer[32]
hexdump &buffer[0] 52
telescope $ebp-0x28 13
x/wx $ebp
x/wx $ebp+4
x/wx $ebp+8
info frame

whatis should report char [32]; sizeof proves its size. Index 31 is the final valid byte and index 32 is the one-past-the-end boundary. hexdump displays 52 bytes: 32 buffer bytes, 8 padding bytes, 4 saved-EBP bytes, 4 saved-return-address bytes, and 4 parameter bytes. A short string writes its characters and a zero terminator; it does not erase the rest of an uninitialized buffer.

The marker contains exactly 48 printable bytes:

9. Watch leave and ret consume the saved values

Find the exact address of the leave instruction in your binary:

Pwndbg
disassemble copy_label

Substitute that address below. This avoids hard-coding an address that could differ after compiler or source changes.

Pwndbg — replace LEAVE_ADDRESS
break *LEAVE_ADDRESS
continue
regs eip ebp esp
nearpc
telescope $ebp 3

Immediately before leave, the live EBP is still a valid frame address. Memory at [EBP] holds 0x42424242, and [EBP+4] holds 0x58585858.

Execute only leave

Pwndbg
si
regs eip ebp esp
nearpc
telescope $esp 2

leave is equivalent to mov esp,ebp followed by pop ebp. Therefore EBP becomes 0x42424242, while ESP advances to the saved-return-address slot. EIP points at ret, and [ESP] is 0x58585858.

Execute only ret

Pwndbg
si
regs eip ebp esp
nearpc

ret takes the four-byte value at [ESP], puts it into EIP, and adds four to ESP. EIP therefore becomes 0x58585858. This is only an obvious marker, not a valid code address. Pwndbg may stop immediately with an invalid program counter or report SIGSEGV when execution is resumed.

Terminology checkpoint: the overflow first changed the saved return address in memory. It did not change live EIP at the moment of copying. EIP changed later, when ret consumed that saved value.

10. What happens to a frame after return?

Returning does not normally erase stack bytes. It restores the caller’s stack state, ending the callee’s local-variable lifetime and making that region available for reuse.

Call patternWhile verify() runs
main calls username, it returns; then password, it returns; then verify.Only main and verify are active. Old username/password bytes may remain, but those frames and buffers no longer exist as valid objects.
main → username → password → verify as nested calls.All four frames are active. Each caller has not returned, so any local buffers in those older active frames still exist.
Sequential calls during verify() Nested calls during verify() Higher addresses Higher addresses ┌──────────────┐ ┌──────────────┐ │ main frame │ │ main frame │ ├──────────────┤ ├──────────────┤ │ verify frame │ │ username │ ← buffer remains active └──────────────┘ ← ESP ├──────────────┤ │ password │ ← buffer remains active username/password bytes may ├──────────────┤ be stale below ESP, but their │ verify │ object lifetimes have ended. └──────────────┘ ← ESP

11. Restore defenses and compare

The vulnerable flags were for observation only. Build a second binary with ordinary protections and replace the unsafe copy with a bounded operation in real software.

Bash — protected comparison build
gcc -m32 -O2 -g -Wall -Wextra -fstack-protector-strong -fPIE -pie -D_FORTIFY_SOURCE=2 -z noexecstack -o stack_lab32_protected stack_lab.c
gdb -q ./stack_lab32_protected
Pwndbg
checksec
quit

Pwndbg’s checksec summarizes hardening such as stack canaries, NX, and PIE. The protected build is a comparison, not a repair of the source-level bug: the correct fix is to prevent an oversized copy, for example by tracking the destination capacity and rejecting or truncating input deliberately.

Why defense in depth matters: a canary can detect some overwrites, NX blocks executing bytes on the stack, and PIE randomizes code locations. None makes an unbounded copy good programming practice.

12. Review questions

  1. Why is &buffer[32] useful even though the final valid element is buffer[31]?
  2. Why can ESP move while EBP remains stable inside a function?
  3. At the post-copy breakpoint, why is live EIP still valid even though [EBP+4] contains 0x58585858?
  4. What does sub esp,0x28 reserve, and why is that larger than the declared array?
  5. Is the value at [EBP+8] the source string itself? Explain.
  6. After copy_label returns, do its old bytes necessarily disappear? Does its buffer remain a valid C object?
Instructor key
  1. It is the one-past-the-end boundary and proves the first address outside the array; calculating it is permitted, dereferencing it is not.
  2. ESP tracks temporary pushes and call-alignment space, while EBP is deliberately used as a stable frame anchor.
  3. The copy changed a future control value in memory. EIP changes only when execution reaches ret.
  4. It reserves 40 bytes: the 32-byte array plus eight bytes of compiler-selected padding/alignment in this build.
  5. No. It holds a four-byte pointer value; following that pointer reaches the string characters.
  6. The physical bytes may remain until reused, but the local object’s lifetime ends and using it afterward is invalid.
